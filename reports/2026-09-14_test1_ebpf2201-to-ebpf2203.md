## Why the byte counts differ

Each layer counts different bytes, and the differences are exactly the
headers:

| Counter | What it counts per packet | Expected excess over iperf3 | Measured excess | Unexplained |
|---|---|---|---|---|
| iperf3 | TCP data only | — | — | — |
| eBPF (`ip->tot_len`) | IP header + TCP header + data | 2,689,723 × 52 B = 139,865,596 | 140,040,100 | +174,504 |
| NIC `rx_bytes` | Ethernet header + IP + TCP + data | 12,209,183 × 66 B = 805,806,078 | 806,078,665 | +272,587 |

52 B is a 20 B IPv4 header plus a 20 B TCP header plus 12 B of TCP
timestamps; 66 B adds the 14 B Ethernet header.

**Packet counts are not comparable.** The TC ingress hook runs after the
kernel has merged incoming packets (GRO), so it counts merged packets:
12,209,183 wire packets arrived as 2,689,723 merged ones, about **4.54 per
merged packet**. Headers are counted once per merged packet, which is why
the eBPF excess uses 2.69 M packets and the NIC excess uses 12.2 M. Compare
**bytes**, not packets, when checking eBPF counts against iperf3 or the NIC.

## Throughput step (56 → 19 Gbps)

At 15:17:08, throughput fell from about 56 Gbps to 19.2 Gbps **within a
single 50 ms sample** and then stayed within ±0.2 Gbps until the end.
Monitoring did not cause this: the NIC counters show the same total, and the
NIC dropped no packets. Observations so far:

- An earlier 100 GiB run at 15:15:14–15:15:57 held about 19.5 Gbps the whole
  time and never reached 56. Test 1 started about one minute after it ended.
- The sender logged 9,367 retransmits.
- A sudden step to a very steady ceiling usually points to a CPU limit on
  one of the hosts (frequency, power or thermal throttling), or to one core
  maxed out. Congestion limits usually wobble more.

Not yet checked: iperf3 version (versions before 3.16 are single-threaded),
CPU governor, per-core CPU use and CPU frequency during the run,
`ethtool -S` `out_of_buffer` / pause counters, and a repeat with the TC hook
detached.

## How to verify a run

Use [`reports/tools/verify_edge.py`](tools/verify_edge.py). It needs the
`redis` Python package, which `ld2606_daos_redis/traffic-simulator/venv` has.
It can run on the central host or on a laptop with Redis (6379) and the
backend (8080) forwarded.

The steps below match how Test 1 was run, with iperf3's text output. Later
tests use `iperf3 -J` together with `compare --iperf-json`, which takes the
reference bytes and time window straight from iperf3's JSON output. Prefer
that method for new runs.

### 1. Before the traffic

On the **receiver**, save the NIC counters and check the MTU:

```bash
ip -s -s link show dev $IFACE
```

On the machine running the script, start recording what the dashboard is
served, and note the start time:

```bash
PY=ld2606_daos_redis/traffic-simulator/venv/bin/python
date +%s
$PY reports/tools/verify_edge.py --src 129.57.178.85 --dest 129.57.178.86 \
    record --out run.jsonl &
```

### 2. Run traffic with a fixed size

```bash
iperf3 -c <dest> -B <src> -n 100G -P 4 -i 1 --timestamps
```

A fixed size (`-n`) gives an exact reference byte count. A fixed duration
(`-t`) does not.

### 3. After the traffic

1. On the receiver, run `ip -s -s link show dev $IFACE` again and subtract
   the "before" values.
2. Stop the recorder: `kill %1`.
3. Find the Unix seconds of the run. Take the first and last seconds above
   1 Gbps and widen the window by a couple of seconds on each side. You can
   also convert the iperf3 `--timestamps` times with `date -d '15:17:01' +%s`
   on the host.
4. Compare everything:

```bash
$PY reports/tools/verify_edge.py --src 129.57.178.85 --dest 129.57.178.86 compare \
    --start 1789413419 --end 1789413455 \
    --ref-bytes 107374182400 \
    --nic-bytes 108180261065 --nic-packets 12209183 \
    --served run.jsonl --per-second
```

### 4. Pass criteria

| Check | Pass when |
|---|---|
| `seconds present` | every second in the window is there |
| `inconsistent seconds` | 0 |
| `unexplained` (eBPF vs iperf3) | within ±0.01%. Background traffic is a few hundred KB; a larger gap means bytes were lost or double-counted |
| `unexplained` (NIC vs iperf3) | the same. This confirms the NIC readings covered only this run |
| `value mismatches vs Redis` | 0 |
| `busy seconds never served` | 0 |
| Dashboard | the edge appears about 3 s after traffic starts and its detail chart follows the per-second series |

The script reads data from Redis, which deletes it after 3600 s, so run
`compare` within an hour of the test. It won't find the data at all if the
DAOS drain worker has already moved it out of Redis.

## Caveats

- **Packet counts:** compare bytes, not packets, because of GRO merging (see
  above).
- **Very large merged packets:** if a very high rate ever makes the eBPF
  bytes come out far below iperf3, check this first. Merged IPv4 packets
  over 64 KB (possible with a raised `gro_max_size`) report an IP length of
  0 and would be counted as 0 bytes. The average merged packet in this run
  was 40 KB, so it did not happen here.
- **Flow limit:** the eBPF map holds at most 2048 flows. That doesn't matter
  for one iperf3 run, but it can for busy multi-host tests.
